# Deployment notes
- **Environments**: separate dev / staging / production, separate DB users, secrets and Redis. Never load real citizen data into dev/staging.
- **Frontend**: build `frontend` (static) behind HTTPS (nginx config included). API and web must share a site (same registrable domain) because cookies are `SameSite=Strict`.
- **Vercel + Render**: Vercel rewrites `/api/v1/*` to the Render API while keeping browser requests same-origin. `vercel.json` is provided at the repository root and under `frontend/`; keep the one inside the Vercel project's configured Root Directory. Set the Render API's `CORS_ORIGIN` to the exact Vercel site origin (for example, `https://samysa-medhi-project.vercel.app`) and redeploy both services. Keep `VITE_API_BASE_URL` unset or set it to `/api/v1`; do not point it directly at the Render hostname because authentication cookies use `SameSite=Strict`.
- **Render API**: use the repository root as the service root, `npm ci` as the build command, and `npm run start -w backend` as the start command. Do not run `npm run build`: the API is plain JavaScript and has no build script. Production `start` reads the platform-injected environment directly and does not load `.env`. The root `.env` is loaded only by local backend/worker development and backend migration/seed scripts. Configure `NODE_ENV=production`, `PORT`, `DATABASE_*` (`DATABASE_SSL=true`), `REDIS_URL`, `JWT_ACCESS_SECRET`, and `CORS_ORIGIN` in the Render dashboard. Confirm `/health` returns HTTP 200 and `/ready` returns HTTP 200 before testing the Vercel API rewrite.
- **Render Worker**: create a separate Background Worker from the repository root, build with `npm ci`, and start with `npm run start -w worker`. Set `NODE_ENV=production` explicitly and supply the same database environment settings as the API, with `DATABASE_SSL=true`. The worker processes queued imports/exports. A job that remains `QUEUED` with zero processed rows indicates the worker is not running against that database. Scale API replicas, then size `DATABASE_CONNECTION_LIMIT` = floor(DB max conns × 0.7 / replicas).
- **TiDB**: use TLS (`DATABASE_SSL=true`), a least-privilege DB user (no DDL at runtime), daily backups + PITR, and **test restores** quarterly.
- **Redis**: required in production (rate limits); protect with auth + TLS.
- **Migrations**: locally, `npm run migrate -w backend` loads the repository-root `.env`; in CI, `node backend/src/scripts/migrate.js` uses the explicit `NODE_ENV=test` and ephemeral TiDB environment. For a release job, run `node backend/src/scripts/migrate.js` with the platform-injected production environment after staging verification; do not use the npm wrapper when no local `.env` is present. Never auto-apply untested migrations to production. Deploy migration `006_import_roster_deletion.sql` before the updated API and worker, and deploy the API and worker together so new imports receive record-tracking IDs required by the admin delete action.
- **Attachment limit rollout**: apply database/migrations/008_attachment_limit_counter.sql before deploying the API version that enforces the three-file limit through complaints.attachment_count.
- **Secrets**: inject via your platform's secret manager; rotate `JWT_ACCESS_SECRET` by deploying a new value (all access tokens expire in ≤10 min).
- **Load testing**: do not claim capacity until measured. Seed 30k synthetic citizens / 10k+ households, then record p50/p95/p99, RPS, error rate, DB latency, pool utilisation.
